# Upstream source runtime probe

This spike compiles the pinned upstream Mindustry LogicOp.java directly from Git. The small driver calls the existing implementation. The official v160.8 server release provides the matching Arc and Mindustry dependencies. Generated code and upstream files stay in the build directory.

## Reproduce

Use Java 17, Gradle 9.3.1, Git, an upstream v160.8 checkout and the [official server JAR](https://github.com/Anuken/Mindustry/releases/tag/v160.8). From this directory, pass absolute input paths.

    gradle -PupstreamCheckout=/path/to/Mindustry -PreferenceJar=/path/to/server-release.jar runProbeJvm generateC

From an x64 Visual Studio developer prompt, compile the generated C.

    cd build\generated\teavm\c
    cl /nologo /std:c11 /O2 all.c /Fe:upstream-logic.exe
    upstream-logic.exe

Both runs should print UPSTREAM_LOGIC quotient=-3 remainder=1 xor=6.

## Continuous verification

[`upstream-arm11-smoke.yml`](../../.github/workflows/upstream-arm11-smoke.yml)
runs the `logic`, `map`, `resource`, `executor`, `campaign-settings` and
`wave-routing` probes for PRs and pushes touching this
directory, then cross-builds each generated C output with the pinned devkitARM
container and uploads the `.3dsx`/ELF artifacts. It also runs the pinned
upstream save-writer, sound/music, sector/tech-tree, and unit/bullet metadata
baselines, and converts the three mapped pinned sounds to PCM16 with provenance.
It uses no secrets and read-only repository permissions. The initial logic/map run was
[44798365837](https://github.com/levkeveli/Min3DStry/actions/runs/44798365837);
the three-probe run including Arc resources is
[44801673667](https://github.com/levkeveli/Min3DStry/actions/runs/44801673667).

Local equivalent (the same three probes, from this directory):

    gradle -PupstreamCheckout=/path/to/Mindustry -PreferenceJar=/path/to/server-release.jar \
        -Pprobe=logic runProbeJvm generateC
    gradle -PupstreamCheckout=/path/to/Mindustry -PreferenceJar=/path/to/server-release.jar \
        -Pprobe=map runProbeJvm generateC
    gradle -PupstreamCheckout=/path/to/Mindustry -PreferenceJar=/path/to/server-release.jar \
        -ParcCheckout=/path/to/Arc -Pprobe=resource runProbeJvm generateC

    # Cross-build the generated C for ARM11 (devkitPro environment):
    bash arm11/build.sh build/generated/teavm/c build/probe-3ds

The resource probe must print
`UPSTREAM_RESOURCE size=709 crc32=3921318438 classpath=ok internal=ok missing=ok`.

## Evidence

- Java 17 and x64 C generated by [TeaVM 0.16.0](https://teavm.org/docs/c-backend/getting-started.html) produced identical results.
- GNU Arm Embedded GCC 15.2.1 with the flags below stopped at a missing newlib uchar.h header. The generated runtime selects Unix APIs for GNU targets, including memory mapping and POSIX signal timers. A 3DS target needs equivalent runtime services.

    arm-none-eabi-gcc -march=armv6k -mtune=mpcore -mfpu=vfp -mfloat-abi=hard -std=gnu11 -c all.c

## ARM11 smoke build

After generating the C, source devkitPro's `3dsvars.sh` and run the following from this directory with Python 3.10+.

```sh
bash arm11/build.sh build/generated/teavm/c build/probe-3ds
```

This produces `build/probe-3ds/upstream-probe.3dsx` and a symbolized ELF. Use a fresh output directory because the staging script copies and adapts the generated runtime files.

Boot the probe in Azahar with the desired console model. The top screen and the emulated debug log should show the same result as Java. For logging, set the Azahar log filter to `*:Info Debug.Emulated:Debug`. START exits the probe.

[Test build 44757615581](https://github.com/levkeveli/Min3DStry/actions/runs/44757615581) linked with devkitARM and libctru. In Azahar 2126.2 Original and New 3DS modes, the build emitted `UPSTREAM_LOGIC quotient=-3 remainder=1 xor=6`, matching the JVM baseline.

The probe provides libctru event waits, clocks, debug output, and a fully backed scratch heap. It aligns dynamic class entries on ARM so TeaVM's compressed references can represent them. It uses TeaVM's small existing character-conversion fallback and a libctru SD adapter for Arc file streams. Full game runtime services, Unicode coverage, physical hardware, gameplay and multiplayer are unverified. See [the port plan](../../docs/upstream-port.md).

## Upstream map metadata probe

Add `-Pprobe=map` to the Gradle command to extract the original Glacier map from the pinned Git revision at build time. The fixture adapter supplies those exact bytes to upstream `MapIO.createMap` through a buffered stream. This keeps Arc's file initialization and executor dependencies outside the metadata test. Run the ARM11 build command with a new output directory after switching probes.

The JVM, native Windows x64 build, and both Azahar 2126.2 modes returned `UPSTREAM_MAP name=Glacier width=150 height=250 version=7`. [devkitARM build](https://github.com/levkeveli/Min3DStry/actions/runs/44759607972)

### Read the map from SD

Generate the probe with `-Pprobe=map-sd`, then use the ARM11 build command with a fresh output directory. In this mode `runProbeJvm` still runs the in-memory Java reference, while `generateC` builds the native SD entry point.

Place the original Glacier input at `/3ds/min3dstry/glacier.msav` on the target SD or Azahar virtual SD. For example, in Bash with `UPSTREAM` and `SD_ROOT` set to the respective directories:

```sh
mkdir -p "$SD_ROOT/3ds/min3dstry"
git -C "$UPSTREAM" show 19a0f40d44514f4802a8b79770456e7e32e34da0:core/assets/maps/default/glacier.msav \
    > "$SD_ROOT/3ds/min3dstry/glacier.msav"
```

TeaVM calls a native buffered read adapter, which opens the file through libctru's SD mount. The upstream parser still performs inflation and metadata decoding. The SD probe expects the original Glacier metadata, and the map bytes are not included in its payload.

[SD build 44761441455](https://github.com/levkeveli/Min3DStry/actions/runs/44761441455) produced the expected metadata from the virtual SD on both Azahar console profiles. Both profiles also reported an error when the file was missing and when given a malformed input, without freezing or crashing.

This checks metadata for one upstream map. Tile and building loading, save state, general-purpose filesystem support, and physical hardware are still unverified.

### Establish the JVM world-loading baseline

Run the baseline with Java 17 and the pinned upstream server JAR. Use a scratch
working directory because upstream initialization creates local data directories.

```sh
java -cp /path/to/server-release.jar \
    /path/to/Min3DStry/research/upstream-runtime/host/UpstreamWorldBaseline.java \
    /path/to/glacier.msav
```

Upstream `World.loadMap` loads Glacier and emits
`UPSTREAM_WORLD width=150 height=250 tiles=37500 buildings=2`. The building count
includes each building once at its origin tile. Use this JVM result as a
reference when bringing up upstream world loading on ARM11.

The source-runtime probe also exercises this path via the staged Arc file
handle and upstream content initialization. With the original Glacier map
extracted as above, run:

```sh
gradle -Pprobe=world -PupstreamCheckout=/path/to/Mindustry \
    -PreferenceJar=/path/to/server-release.jar -ParcCheckout=/path/to/Arc \
    runProbeJvm --args=/path/to/glacier.msav generateC
```

The probe uses the same seed on each platform for Glacier's upstream map
filters. It verifies 37,500 populated tiles, two `core-nucleus` building
origins at (81, 26) and (81, 224), and fingerprint `2e7b9f883994de6c`.
The fingerprint covers floor, overlay, block, and building links for each
tile, plus team and rotation at each building's origin. The probe also checks
saved construction statistics, the enemy core protection radius, and the
first wave group through the upstream JSON reader.
The unmodified v160.8 server JAR and the generated Windows x64 executable
with the reflection runtime patches produced the same result.
To reproduce the Windows check, run
`python3 arm11/fix_reflection_lifetime.py build/generated/teavm/c`
before compiling, then pass the path to Glacier to the executable.

With a second path, the probe calls upstream `SaveIO.load` on a v13
save generated by the pinned Java writer from the same world. The test
fixture contains a point marker with ID 37 at (80, 152). The test checks
the world fingerprint again and verifies that the marker was restored.
This check passed on the JVM and generated Windows x64 C.
With the same Gradle properties used above and a new output path, run
`makeWorldSaveFixture --args="/path/to/glacier.msav /path/to/generated-save.msav"`.
Then run `runProbeJvm --args="/path/to/glacier.msav /path/to/generated-save.msav"`
or pass both paths to the Windows executable. Look for
`UPSTREAM_SAVE version=13 marker=ok`.

The C build recompiles two compiler classes from the hash-checked TeaVM
0.16.0 source archive. The patches retain the original entry block's
liveness during coroutine splitting and use the primitive array opcode to
infer the value type of each element. For offline generation, pass an
already downloaded source archive with
`-PteavmCompilerSources=/path/to/teavm-core-0.16.0-sources.jar`.

Generate the ARM11 probe with the build command above and install the same
original Glacier file at `/3ds/min3dstry/glacier.msav` on the target SD.
The ARM11 build uses `-fwrapv` to retain Java's signed integer wraparound.
The staging script keeps every managed heap allocation eight-byte aligned
so a compaction move preserves the layout of `long[]` and `double[]`.
The probe reserves a 256 KiB native stack for the generated serializer.

Use `-Pprobe=world-save` to load both fixtures. Copy the generated v13 save
to `/3ds/min3dstry/glacier-v13.msav`. Use `-Pprobe=world-roundtrip` to also
write and reload `/3ds/min3dstry/glacier-roundtrip.msav`. The round trip
reserves a new output file and rejects an existing destination. The probe also
checks the new file through `SaveIO.isSaveValid` before reloading it. On the
JVM, pass the map, v13 input, and new output paths as arguments. The
round-trip check ends with `UPSTREAM_SAVE_ROUNDTRIP version=13 marker=ok`.

The host-side [save resilience probe](host/README.md#save-resilience-checks)
uses the same pinned server JAR and Glacier fixture to reject truncated,
bad-header and unknown-version saves and to exercise the upstream backup path.
Port-side `MIN3DSTRY_SAVE_POLICY` checks separately verify that an injected
write failure leaves no final or temporary save. It runs without devkitARM; the
ARM11 write path still uses a new output file and rejects an existing
destination.

[DevkitARM test builds with standard flags](https://github.com/levkeveli/Min3DStry/actions/runs/44793525705)
and [with C optimization disabled](https://github.com/levkeveli/Min3DStry/actions/runs/44792277588)
matched the v7 map, v13 input, and v13 output world fingerprints in both
Azahar 2126.2 console profiles. The unmodified v160.8 server JAR loaded
the files written on emulated SD and found marker 37 at (80, 152).

The standard build's ELF load segments total 32.63 MiB rounded to pages.
Including its 16 MiB managed heap reservation and 256 KiB native
stack brings those components to 48.88 MiB. This subtotal leaves
15.12 MiB of a 64 MiB application budget for the rest of the runtime.
Physical hardware measurements still need to account for allocator
metadata, direct buffers, graphics, and the operating environment.

Graphics and audio JNI methods reached by compiler analysis throw if
called in this headless mode. Broader save coverage and physical-device
verification remain open in #28.

### Load a v160.8 multiplayer world snapshot

The `world-stream` probe feeds the compressed `WorldStream` payload to
the same upstream `NetworkIO.loadWorld` entry point as
`core/src/mindustry/core/NetClient.java` in pinned Mindustry v160.8.
The capture uses that release's Arc client, `PacketSerializer` and
`StreamBuilder`. The staged source extracts an overload that reports
entity IDs through a callback. The regular entry point still forwards
those IDs to `NetClient`. The probe records them locally so it can test
the deserializer before the 3DS client registers its network and UI
handlers.

In a scratch directory start the official `server-release.jar` and enter
`config port 16568` followed by `host Glacier`. With the local server
running, capture a new fixture from the repository root:

```sh
java -cp /path/to/server-release.jar \
  research/upstream-runtime/host/UpstreamWorldStreamCapture.java 16568 /path/to/glacier-world-stream.bin
```

Run `runProbeJvm` with `-Pprobe=world-stream` and pass the fixture path
through `--args`. The probe prints world dimensions, building origins,
the terrain fingerprint, rules and the local player ID and team. The
ARM11 entry point reads the same fixture from
`/3ds/min3dstry/glacier-world-stream.bin` on the SD.
Reuse the same capture when comparing platforms because each server
startup can produce different filter results and tick state.

Two captures from fresh official servers on loopback loaded the 150 × 250
map, both cores, wave 1 and the assigned player. The pinned JVM, generated
Windows x64 program and [ARM11 build](https://github.com/levkeveli/Min3DStry/actions/runs/44819568048)
reported matching state for each corresponding capture. Both Azahar 2126.2
console profiles reported the terrain fingerprints `cd909fce1d821404`
and `eabf9af0dd63684c` for the two captures, respectively.

Run the comparison from the repository root with the exact
`UPSTREAM_WORLD_STREAM ...` line from `runProbeJvm`:

```sh
python tools/verify_upstream_world_stream.py --rom /path/to/upstream-probe.3dsx \
  --azahar /path/to/azahar --fixture /path/to/glacier-world-stream.bin \
  --reference "$jvm_world_stream_line"
```

The ARM11 ELF load segments occupy 25.39 MiB after page rounding.
With its 16 MiB managed heap and 256 KiB native stack, those components
total 41.64 MiB. Physical-console memory and networking still need testing.
Live 3DS sockets, connection confirmation and gameplay synchronization
are tracked in #44.

### Arc `settings.bin` round-trip

`-Pprobe=campaign-settings` uses the real upstream Arc `Settings` class rather
than a native reimplementation. It writes a fresh `settings.bin` under the Java
temporary directory, reloads it with a second `Settings` instance, verifies an
integer and string value, and prints:

```text
UPSTREAM_CAMPAIGN_SETTINGS path=live bytes=112 int=12345 string=ok campaign=unlocked:conveyor,research:50 reload=ok
```

The JVM uses a temporary directory and reports `path=tmp`. On 3DS the probe
targets the live `/3ds/min3dstry`, snapshots existing settings/backup/backups,
runs the round-trip (including upstream campaign unlock/research keys), then
restores or removes the prior state. The ARM11 probe
is built with the normal `arm11/build.sh` command; both Azahar 2126.2 profiles
reported `path=live`.

### Sector slot `.msav` round-trip

`-Pprobe=campaign-sector` writes the real `sector-serpulo-170.msav` slot through
upstream `SaveIO`, verifies it via `SaveIO.isSaveValid`/reload, prints
`UPSTREAM_CAMPAIGN_SECTOR slot=sector-serpulo-170.msav ... version=13 marker=ok`,
and removes the slot. The same probe is built for ARM11 in the
`world-roundtrip` CI job. Azahar 2126.2 New and Old profiles both reported the
marker and left no slot file behind.

### Campaign content unlock state

`-Pprobe=campaign-content` verifies conveyor is locked with empty settings,
persists the upstream `conveyor-unlocked` and `req-conveyor-copper` settings,
reloads a fresh `Settings` from `settings.bin`, rebuilds content, and checks
`Blocks.conveyor.unlocked()` only from the reloaded state. JVM and ARM11/Azahar
report:

```text
UPSTREAM_CAMPAIGN_CONTENT path=live lockedBefore=ok conveyorUnlocked=true key=conveyor-unlocked research=50 reload=ok blocks=447
```

The probe snapshots and restores live settings on 3DS; Azahar 2126.2 New and
Old profiles both reported the marker and left no `settings.bin` behind.

### Join the upstream server from the ARM11 probe

`-Pprobe=network-live` uses the same upstream deserializer with live
libctru TCP and UDP sockets. The native bridge retains the Arc transport
after registration and exposes packet IDs and payloads. The Java entry
point reads the original `StreamChunk` packets as an input stream and
calls `NetworkIO.loadWorld`. It writes the generated `ConnectConfirmCallPacket`
and decodes the generated `StateSnapshotCallPacket` class.

Generate C with `-Pprobe=network-live`. Pass `--network` as the final
argument to `arm11/build.sh`. Stage a plain-text host and port in
`/3ds/min3dstry/server-endpoint.txt`, separated by whitespace. Run a
local official v160.8 server hosting Glacier. The probe attempts an
outdated build, then joins and disconnects twice with its test identity.
The `UPSTREAM_LIVE_NET_*` records report each step.

The emulator verifier starts a fresh official server for each console
profile, stages the loopback endpoint, and compares the emulator and
server records. Run from the repository root:

```sh
python tools/verify_upstream_live_net.py --rom /path/to/upstream-probe.3dsx \
  --azahar /path/to/azahar --server /path/to/server-release.jar
```

The live probe also calls the generated state and entity snapshot packets'
original client handlers. It stages the pinned `NetClient.java` with a
separate constructor for frontends that manage packet dispatch themselves.
The original snapshot methods and desktop constructor behavior are preserved.
The verifier hosts Glacier in Attack mode so the enemy core supplies
upstream ground spawns. It issues the official server's `runwave` command
after the first state snapshot on each join. It then checks for an advanced
wave and a newly created Dagger entity in the client world. The second join
waits beyond the server's 12-second TCP timeout to exercise Arc keepalive.
The regular connection UI, outgoing
player actions and other live packet handlers are tracked in #44.

For the host reference, run `runProbeJvm` with `-Pprobe=network-live`
and pass a captured `WorldStream` file through `--args`. The JVM
version uses upstream item and unit serialization to verify the applied
wave, clock, core copper inventory and Dagger entity coordinates.

The [snapshot dispatch build](https://github.com/levkeveli/Min3DStry/actions/runs/44828359834)
passed on the Old and New 3DS profiles in Azahar 2126.2 at both `-O0`
and `-O2`. Each run rejected build 159, joined the stock v160.8 server,
applied wave 1 → 2, then rejoined and applied wave 2 → 3 after a
13-second wait. Each join registered a different Dagger in the upstream
sync group. The second join logged a TCP keepalive during the wait, and

### Build and remove blocks with the touchscreen

The graphical multiplayer probe shows a bottom-screen palette after it
loads Glacier. Select Conveyor or Copper Wall, then tap the matching cell
in the bottom grid. The grid follows the 16 × 12 viewport on the top
screen. Rotate turns rotatable blocks a quarter turn. Remove toggles
deconstruction and gives the cursor a red outline. A submits at the
cursor, R rotates, and B toggles removal. For a placed Sorter or Inverted
Sorter, tap Config beside the grid, then tap the building. Select an
item or tap the active item again to clear it. The choices use the
original item eligibility rule from `ItemSelection.java`.

The multiplayer image keeps the original v160.8 translation bundles in
RomFS. It loads the 3DS system language through Arc's `I18NBundle` before
creating content so categories, blocks and items use the game's names.
To choose a packaged locale for the graphical probe, put its code in
`/3ds/min3dstry/locale.txt` on the SD card. For example, use `de` for
German or `pt_BR` for Brazilian Portuguese. A missing or unknown code
uses the console language. Some controls specific to the 3DS probe still
use English labels.

The touchscreen block catalog and Sorter item menu draw their original
icons. Multiplayer asset preparation uses the stock v160.8 registry and
`UnlockableContent.loadIcon` to select each texture by the upstream ID.
It exports 425 block icons and all 22 item icons. The renderer keeps up
to six icon textures resident, with a combined texel budget of at most
384 KiB. It replaces each row's old texture after the preceding GPU
frame completes.

To verify the original crops and 3DS texture pixels independently, run
these commands from the repository root with the pinned asset and server
JARs and tex3ds v2.3.0 on PATH. The first command writes to a new
verification directory.

```sh
mkdir menu-icon-reference
java -Djava.awt.headless=true -cp /path/to/server-release.jar \
  tools/UpstreamSpriteAtlas.java /path/to/assets.jar menu-icon-reference --menu-icons
java tests/tools/VerifyUpstreamMenuIcons.java menu-icon-reference
```

The verifier compares the generated headers, alpha bytes and all visible
RGBA texels against devkitPro's tex3ds output. It compares transparent RGB
against the exported PNG because tex3ds clears RGB where alpha is zero.

Add `--menu-icons` to the `--touch-config --controls-replay` verifier
to check six rendered block icons and six item icons in both touchscreen
captures.

The [icon build](https://github.com/levkeveli/Min3DStry/actions/runs/44857778814)
passed this replay on both Azahar 2126.2 profiles with German labels.
Both captures showed the original Distribution and Sorter menu icons.
The stock server accepted the same Copper, Lead and clear configuration
sequence and both clients reached wave 2 and disconnected normally.

### Original v160.8 font rasterization

### Capture upstream Glacier terrain commands

[Issue #73](https://github.com/levkeveli/Min3DStry/issues/73) exercises the
renderer boundary without a graphics context. Arc reads `sprites.aatls`
from the [pinned v160.8 release](https://github.com/Anuken/Mindustry/releases/tag/v160.8).
Each page descriptor supplies its original dimensions so Arc computes
the same UVs for full sprites and split regions. No page images are
needed for this probe. It calls upstream `Floor.load` and `Floor.drawBase`
over a 16 × 12 viewport near the first copper tile in the original
Glacier world. A Batch captures the order, texture page, UVs, geometry,
and packed color and mix color of the draw requests.

The pinned `Floor.drawBase` calls `drawOverlay`, which submits ore
sprites as part of that floor pass.

With the verified official `assets.jar` from the
[sprite pipeline](../../docs/rendering/asset-pipeline.md), extract the
original atlas file into your scratch directory.

```sh
unzip -p /path/to/assets.jar assets/sprites/sprites.aatls > /path/to/sprites.aatls
gradle -PupstreamCheckout=/path/to/Mindustry -PreferenceJar=/path/to/server-release.jar \
  -ParcCheckout=/path/to/Arc -Pprobe=terrain-draw \
  runProbeJvm --args='/path/to/glacier.msav /path/to/sprites.aatls' generateC
```

The unmodified v160.8 JVM classes, adapted JVM build, and generated
Windows x64 C executable emitted this trace:

```text
UPSTREAM_TERRAIN viewport=18,0+16x12 commands=320 copper=26 edges=88 hash=de709773b1b58465
```

To check the original JVM classes, compile the probe and
`UpstreamWorldLoadProbe.java` against the unmodified server JAR, then
run `UpstreamTerrainDrawProbe` with the same two paths. To check the
generated C, run `arm11/fix_reflection_lifetime.py` on a scratch copy of
the generated directory before compiling `all.c` with the host compiler.
Pass the same two paths to the executable. The ARM11 build script applies
the reflection fix during staging.

For the ARM11 probe, put the original `glacier.msav` and `sprites.aatls` in
`/3ds/min3dstry/` on the SD card.
[DevkitARM build 44799955644](https://github.com/levkeveli/Min3DStry/actions/runs/44799955644)
used the standard `-O2` flags. Both Azahar 2126.2 console profiles
emitted the identical terrain trace and Glacier world fingerprint.
The trace precedes the Citro2D presentation step tracked in #38.

[The integration build](https://github.com/levkeveli/Min3DStry/actions/runs/44833286449)
reproduced the same 320 commands, 26 copper draws, and hash on both
Azahar console profiles after combining the probe with the merged world loader.

The current viewport uses 13 upstream atlas regions. A local build of
that set with tex3ds v2.3.0 produced a 128 × 256 RGBA8 page (128 KiB).
To reproduce the page, pass the names below, in this order, to the

### Build the Citro2D terrain viewport

[Issue #75](https://github.com/levkeveli/Min3DStry/issues/75) connects
